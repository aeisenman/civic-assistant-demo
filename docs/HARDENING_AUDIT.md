async def request_context(request, call_next):

## The five I would lead with

1. **The chat stream deadlocks at 20 concurrent users and there is no alarm for it.** The SSE route holds a pool connection in a `yield` dependency for the life of the stream and then asks for a second one. Below 20 it is 0.3 s; at 20 every resident waits 60 s and is told something went wrong; at 50, 30 of them get an HTTP 500. The code comment says the dependency "is closed before the body streams" — it is not. One-line class of fix, and the single highest-value thing to do before any launch.
2. **`MAX_CONCURRENT_STREAMS` is admission control in the wrong place.** It is acquired after the 200 and the headers are already on the wire, so no load balancer can shed and no client sees backpressure. Raising it to 64 changed nothing measurable. Backpressure has to be a 429 before the response starts.
3. **Nothing in this stack survives a second replica.** Stream cap, login throttle, workflow worker and KB ingest are all in-process; `kb_documents.filename` has no unique constraint, so two booting replicas silently double the knowledge base. Migrations are locked; ingest is not. Horizontal scaling is currently a data-corruption event, not a config change.
4. **Two sync calls sit on the event loop in the worst possible places.** The certificate render+PUT runs inside a `FOR UPDATE` row lock, and boto3 has no timeouts (60 s × 3). A slow — not dead — object store stalls every in-flight stream and the healthcheck. `intake.py` already shows the `to_thread` pattern; it just was not applied here.
5. **Time and privacy are both unowned.** Tools use `date.today()` in a UTC container while the prompt says `America/Los_Angeles`, so after 5 pm PT the assistant contradicts itself about trash day and mints 2027 tracking numbers on New Year's Eve; meanwhile every resident message, address and phone number sits in `traces` forever, readable in full by any of the one staff accounts, with no retention job and no RBAC.
